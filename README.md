# Auction-server

옥션 중고 경매 시스템과 유사한 기능을 가지는 중고 경매 서비스 백엔드 서버입니다.  
회원, 상품, 경매, 입찰, 결제, 검색까지의 흐름을 백엔드 관점에서 설계하고 구현했습니다.

특히 경매 서비스에서 자주 발생하는 검색 성능 문제와 입찰 처리 부하를 직접 다루는 것을 목표로 했으며,  
단순 기능 구현을 넘어서 객체지향 설계, 성능 개선, 비동기 처리 경험에 중점을 두었습니다.

- 참고 서비스: [Auction 중고장터](https://corners.auction.co.kr/corner/UsedMarket.aspx)

---

## 프로젝트 목적

이 프로젝트는 단순한 중고 경매 기능 구현을 넘어서,  
실제 서비스(옥션 중고장터)와 유사한 도메인을 기반으로 백엔드 핵심 역량을 연습하는 것을 목표로 했습니다.

구체적으로는 다음과 같은 목적을 두고 설계하고 구현했습니다.

- **도메인 모델링 연습**  
  - 회원, 상품, 경매, 입찰, 결제, 알림 흐름을 객체지향적으로 모델링하고,  
    엔티티 중심으로 읽기 쉬운 코드를 유지하는 연습을 했습니다.

- **JPA 기반 개발 경험**  
  - 기존 SQL 위주 개발 방식에서 벗어나, JPA를 활용해 엔티티와 연관관계를 설계하고,  
    복잡한 조회와 상태 전이를 JPA 기반으로 처리하는 경험을 쌓았습니다.

- **대용량 조회 및 검색 성능 개선**  
  - 경매 서비스 특성상 검색 트래픽과 정렬·필터 조건이 복잡해질 수 있기 때문에,  
    RDB 기반 검색의 한계를 성능 테스트로 확인하고 Elasticsearch를 도입해 성능을 개선했습니다.

- **입찰 처리 부하와 비동기 메시징 처리**  
  - 인기 경매 상품에 입찰 요청이 몰리는 상황을 가정하고,  
    RabbitMQ 기반 비동기 메시징 구조를 통해 서버 부하를 분산하고 안정적으로 처리하는 방식을 연습했습니다.

- **성능 테스트와 검증 가능한 코드 구조**  
  - Locust로 주요 API(검색, 입찰, 경매 조회)에 대한 목표 TPS를 설정하고,  
    성능 테스트 결과를 기반으로 병목을 찾고 개선하는 과정을 경험했습니다.  
  - 동시에 단위 테스트·통합 테스트를 통해 도메인 로직을 검증 가능한 구조로 유지하는 것을 중요하게 생각했습니다.

## 경매 판매 방식 (도메인 규칙)

실제 옥션 중고 경매 서비스의 판매 방식 안내를 참고하여,  
이 프로젝트에서는 다음과 같은 경매 규칙을 도메인 로직에 반영했습니다.

- 참고: https://sell3.auction.co.kr/sellbasic/Popup/sell_pop_system.html

<details>
<summary>Auction-server 경매 규칙 자세히 보기</summary>

### 1. 시작가 및 즉시 구매가 규칙

- 경매 시작 금액은 1,000원 이상부터 설정할 수 있으며,  
  필요한 경우 즉시 구매가를 함께 등록할 수 있습니다.
- 판매자는 상품 등록 시 시작가와 즉시 구매가를 함께 설정하여,  
  경매로 천천히 판매할지, 즉시 구매로 빠르게 판매할지 선택할 수 있습니다.

이 규칙을 둔 이유는 다음과 같습니다.

- 비정상적으로 낮은 가격 등록을 줄이고 싶었습니다.  
- 구매자에게는 경매 종료를 기다리지 않고 바로 구매할 수 있는 선택지를 제공하고자 했습니다.  
- 판매자는 최소 희망가와 즉시 판매가를 나누어 상황에 맞는 전략을 취할 수 있습니다.

---

### 2. 입찰 후 핵심 정보 수정 불가 규칙

- 한 번이라도 입찰이 발생한 상품은 가격, 경매 기간 등 핵심 정보를 수정할 수 없고,  
  상세 설명만 추가할 수 있습니다.

이 규칙을 둔 이유는 다음과 같습니다.

- 입찰이 진행 중인 상품의 조건이 중간에 바뀌면 기존 입찰자가 불리해질 수 있습니다.  
- 판매자가 경매 도중 조건을 바꾸며 무분별하게 입찰을 유도하는 상황을 막고자 했습니다.  
- 입찰자는 처음 확인한 조건을 기준으로 경매에 참여해야 공정성이 유지된다고 판단했습니다.

구현 측면에서는, 입찰 이력이 존재하는 상품에 대해  
가격·기간 등 핵심 필드 수정 요청을 차단하고, 상세 설명만 수정 가능하도록 도메인 로직을 분리했습니다.

---

### 3. 무분별한 입찰 방지를 위한 검증 규칙

이 프로젝트에서는 단순히 입찰 기능만 구현하는 데서 끝나지 않고,  
반복 요청이나 의미 없는 중복 입찰을 줄이기 위한 검증 로직도 함께 고려했습니다.

예를 들어 다음과 같은 상황을 방지하고자 했습니다.

- 동일 사용자가 같은 상품에 동일 금액으로 여러 번 요청을 보내는 경우  
- 실제 구매 의도 없이 반복 요청만 보내는 경우  
- 입찰 기록을 불필요하게 증가시키는 비정상 요청

이를 위해 입찰 요청 시 `물품 ID`, `입찰자 ID`, `입찰 금액` 조합으로  
이전과 동일한 요청이 존재하는지 확인하는 검증 로직을 두었습니다.

이를 통해 무분별한 반복 입찰 요청을 줄이고,  
입찰 기록의 신뢰성을 높이며,  
인기 상품에 요청이 몰릴 때 불필요한 처리 부하를 줄이고자 했습니다.

---

### 4. 낙찰 및 결제 흐름

경매 종료 시점에는 가장 높은 입찰 금액을 기준으로 낙찰자를 결정하고,  
낙찰자에 대해 결제 요청이 진행되도록 구성했습니다.

이 프로젝트에서는 다음과 같은 흐름으로 처리합니다.

1. 경매 종료 시, 해당 상품의 최고 입찰 금액과 입찰자를 조회합니다.  
2. 최고 입찰자를 낙찰자로 선정하고, Toss Payments 결제 요청/승인 API를 호출합니다.  
3. 결제가 정상적으로 완료되면, 상품 상태를 배송 단계로 변경합니다.  
4. 결제 취소나 환불이 필요한 경우, 취소/환불 API를 통해 후속 처리를 진행합니다.

---

### 5. 입찰 흐름 예시

예를 들어, 다음과 같은 흐름을 가정할 수 있습니다.

1. 판매자가 중고 카메라를 경매 상품으로 등록합니다.  
   - 시작가: 50,000원  
   - 즉시 구매가: 120,000원

2. A 사용자가 60,000원으로 최초 입찰을 진행합니다.  
   이 시점부터 해당 상품은 가격이나 기간 같은 핵심 정보를 수정할 수 없고,  
   판매자는 상세 설명만 추가할 수 있습니다.

3. B 사용자가 70,000원으로 재입찰합니다.  
   동일 사용자가 같은 금액으로 반복 요청을 보내더라도,  
   서버는 `상품 ID + 사용자 ID + 입찰가` 조합으로 이미 처리된 요청인지 검증하여 중복 입찰을 제한합니다.

4. 경매 종료 시점에 최고 입찰자인 B가 낙찰자로 선정됩니다.

5. 서버는 낙찰자에게 결제 요청을 보내고,  
   결제가 완료되면 상품 상태를 다음 단계(예: 배송 준비)로 변경합니다.

이와 같은 흐름을 통해,  
이 프로젝트는 단순한 입찰 기능 구현을 넘어서  
경매 서비스의 공정성과 실제 처리 흐름을 함께 고려한 백엔드 서버를 목표로 했습니다.

</details>

- 카테고리 관리  
  - 카테고리별 입찰 단위 설정

- 상품 목록 조회 및 관리

---

### 4. 상품 검색

- 상품명, 판매자, 카테고리 기준 검색
- 입찰자 수 기준 정렬 (입찰이 많은 순)
- 즉시 구매가 기준 정렬 (최저 / 최고 순)
- 입찰가 기준 정렬 (최저 / 최고 순)
- 텍스트 기반 초성 검색 지원

---

### 5. 입찰 및 즉시 구매

- 즉시 구매
  - 즉시 구매가로 입찰 시 Toss Payments 결제 요청/승인 API 연동
- 일반 입찰
  - 최소/최대 입찰 가능 금액, 입찰 단위 검증
  - 입찰 종료 시 최고가 입찰자에 대해 Toss Payments 결제 요청/승인 API 연동
- 입찰 유효성 체크
  - `물품 ID`, `입찰자 ID`, `입찰 금액` 조합으로 이전에 동일 요청이 있었는지 확인하여 중복/무의미한 입찰 방지
- 입찰 히스토리 기록
  - 입찰 시간, 입찰자, 입찰 금액, 판매자, 즉시 구매가 등의 이력을 저장

---

### 6. 알림 및 경매 이력

- 알림
  - 경매 시작/종료 알림
  - 새 입찰 발생 시 알림
  - 경매 결과 알림
- 경매 이력 조회
  - 사용자의 개인 경매 참여 기록 조회
  - 특정 상품의 전체 경매 기록 조회  
    (입찰 ID, 입찰 일자, 입찰 금액 등)

---

### 7. 결제 관리

- Toss Payments 결제 연동
  - 결제 승인 API 연동
  - 결제 취소 API 연동
  - 결제 환불 API 연동
- 결제 이력 조회
- 결제 요청 유효성 체크
  - 결제 금액, 물품 상태 등을 검증하여 정상적인 결제 요청인지 확인

## 입찰 API 시퀀스

입찰 API 시퀀스 다이어그램은 로그인한 사용자가 입찰 요청을 보낸 뒤,  
유효성 검증과 비동기 처리, 이메일 알림까지 이어지는 전체 흐름을 보여줍니다.

![입찰 API 시퀀스](https://github.com/gamsayeon/Auction-Server/assets/75170367/fe69e60c-2e34-4369-a10e-414de1306fb2)

### 구현 설명
- 컨트롤러/서비스에서 기본 유효성 검사(최고 입찰가, 입찰 단위, 입찰 가능 시간 등)를 수행합니다.
- 유효한 입찰 요청만 RabbitMQ 큐에 적재하고, MQ Listener에서 비동기적으로 처리해 DB에 반영합니다.

---

## 결제 API 시퀀스

결제 API 시퀀스 다이어그램은 사용자가 Toss Payments를 통해 결제를 진행할 때,  
결제 생성부터 승인/실패 처리, 경매 상태 변경까지의 흐름을 보여줍니다.

![결제API 시퀀스](https://github.com/gamsayeon/Auction-Server/assets/75170367/9b96376d-bf54-4d62-bd0a-a5b63740de89)

### 구현 설명
- 사용자는 Toss Payments 결제 페이지로 리다이렉트되어 결제를 진행합니다.
- 결제 성공/실패에 따라 Toss에서 설정한 redirect URL로 결과가 전달되고,  
  서버는 승인 API 또는 실패 처리 API를 호출해 결제 상태를 확인합니다.
- 결제가 성공하면 서비스 계층에서 결제 상태를 업데이트하고,  
  JPA를 통해 DB의 결제 정보와 경매/상품 상태(낙찰, 종료 등)를 변경합니다.
- 결제 실패나 예외 상황에서는 로그를 남기고, 필요 시 재시도나 사용자 안내를 할 수 있도록 구성했습니다.

---

## 검색 API 시퀀스

검색 API 시퀀스 다이어그램은 사용자가 키워드와 정렬/페이징 정보를 전달했을 때,  
Elasticsearch를 통해 검색을 수행하고 결과를 반환하는 과정을 보여줍니다.

![검색 API 시퀀스](https://github.com/gamsayeon/Auction-Server/assets/75170367/a7a244e8-f00b-4f47-a924-30c43c9973fe)

### 구현 설명
- 사용자는 상품명, 판매자, 카테고리, 상세 설명 등을 기준으로 검색 요청을 보냅니다.  
  이때 정렬 조건과 페이지 정보도 함께 전달합니다.
- 컨트롤러는 검색 키워드와 페이지 정보를 서비스 계층으로 전달하고,  
  서비스는 Elasticsearch 쿼리를 생성해 검색을 수행합니다.
- Elasticsearch에서 검색 결과(SearchHits)를 조회한 뒤,  
  이를 SearchProductDTO 목록으로 매핑하고 페이지 정보와 함께 응답 본문으로 반환합니다.

</details>

경매 서버의 성능을 검증하기 위해 성능 테스트 계획서를 작성한 뒤 테스트를 진행했습니다.  
이번 테스트의 대상은 검색 API, 입찰 조회 API, 입찰 API입니다.

주요 API의 예상 요청 수와 동시 사용자 수를 기준으로 목표 TPS를 설정했습니다.

- 상품 검색 API  
  - 분당 약 300회 호출
  - 동시 사용자 100명 예상
  - 목표 TPS: 500

- 입찰 조회 API  
  - 분당 약 100회 호출
  - 동시 사용자 100명 예상
  - 목표 TPS: 160

- 입찰 API  
  - 분당 약 30회 호출
  - 동시 사용자 30명 예상
  - 목표 TPS: 15

## 설계와 구현 포인트

이 프로젝트는 단순히 기능을 동작시키는 수준을 넘어서,  
경매 서비스에서 자주 발생하는 문제를 어떤 구조로 해결할지 고민하며 설계했습니다.

특히 객체지향적인 도메인 모델링, 입찰 요청 처리의 비동기화,  
검색 성능 개선을 핵심 설계 포인트로 두고 구현했습니다.

### 1. JPA를 활용한 객체 중심 설계

기존에는 SQL 중심으로 데이터를 다루는 방식에 익숙했지만,  
이 프로젝트에서는 경매, 입찰, 결제처럼 상태 변화가 많은 도메인을  
객체 중심으로 설계하고 관리하는 경험을 쌓고자 했습니다.

이를 위해 JPA를 적용하여 엔티티와 연관관계를 중심으로 도메인을 구성했고,  
복잡한 비즈니스 로직을 단순 쿼리 조합이 아니라 도메인 흐름 중심으로 표현하고자 했습니다.

주요 설계 포인트는 다음과 같습니다.

- 회원, 상품, 입찰, 결제 간의 연관관계를 엔티티 수준에서 명확히 표현.
- 엔티티 상태 변화(경매 시작/종료, 낙찰, 결제 완료 등)를 도메인 로직으로 다룸.
- DTO와 엔티티의 역할을 구분해, 조회 응답과 내부 모델을 분리.

---

### 2. RabbitMQ를 활용한 입찰 처리 비동기화

경매 서비스의 입찰 기능은 특정 시점에 요청이 집중될 가능성이 높습니다.  
모든 입찰 요청을 동기적으로 처리하면 응답 지연과 DB 부하가 커질 수 있다고 판단했습니다.

이 문제를 완화하기 위해 RabbitMQ 기반 비동기 처리 구조를 적용했습니다.

- 컨트롤러/서비스에서 입찰 가능 시간, 최소/최대 금액, 입찰 단위 등 기본 유효성 검사를 수행합니다.
- 유효한 입찰 요청만 RabbitMQ 큐에 적재하고, MQ Listener에서 비동기적으로 처리해 DB에 반영합니다.
- 비동기 구조 특성상 HTTP 응답 시점에는 최종 상태를 확정하기 어려워,  
  AWS SES 이메일 알림을 통해 입찰 성공 여부를 명확히 안내하도록 구성했습니다.

이 구조를 통해 인기 상품에 요청이 몰릴 때에도 서버 응답 지연을 줄이고,  
DB 부하를 분산하며 입찰 이벤트 처리의 신뢰성을 확보하는 것을 목표로 했습니다.

---

### 3. Elasticsearch를 활용한 검색 성능 개선

경매 서비스에서는 상품 검색 기능의 사용 빈도가 높고,  
상품명, 판매자, 카테고리, 상세 설명, 정렬/필터 조건을 함께 사용하는 경우가 많습니다.

초기에는 RDB 기반 LIKE 검색으로 구현했지만, 검색 정확도와 응답 시간,  
복잡한 정렬·필터 조합에서 성능 한계를 확인해 Elasticsearch 도입을 결정했습니다.

적용 시 중점적으로 본 부분은 다음과 같습니다.

- 텍스트 기반 검색 성능 개선과 정렬/필터 조건 처리 최적화.
- 검색 요청에 대한 목표 TPS 달성을 위한 구조 개선.
- 향후 검색 조건 확장(예: 초성 검색, 복합 정렬)에 유연하게 대응할 수 있는 설계.

Elasticsearch 도입 전 성능 측정, 데이터 마이그레이션, 인덱스 매핑,  
도입 후 성능 개선 과정은 아래 글에 정리했습니다.

- [경매 서버 성능 최적화: 경매 서버의 Elasticsearch 도입](https://gamsayeon.tistory.com/56)

## 성능 테스트와 개선

성능 테스트 계획서를 바탕으로 검색 API, 입찰 조회 API, 입찰 API에 대해 부하 테스트를 진행했습니다.  
목표는 경매 서비스 특성에 맞는 요청량과 동시 사용자 수를 가정했을 때,  
각 API가 설정한 목표 TPS를 만족하는지 확인하고 개선 방향을 찾는 것이었습니다.

<details>
<summary>성능 테스트 결과 자세히 보기</summary>

### 1. 검색 API

검색 API는 가장 사용 빈도가 높고, 정렬·필터 조건이 복잡하게 조합될 수 있는 구간입니다.  
Elasticsearch 도입 전에는 RDB 기반 LIKE 검색으로 성능 테스트를 진행했습니다.

- 테스트 시나리오
  - 최대 500명의 동시 사용자가 초당 100번 검색 요청을 보내는 상황을 가정했습니다.
- 결과 요약
  - 평균 TPS: 57 TPS
  - 목표 TPS: 500 TPS

검색 API는 목표 TPS의 약 10% 수준만 달성하여,  
현재 JPA 동적 쿼리 기반 검색 방식으로는 성능 한계가 뚜렷하다는 것을 확인했습니다.  
특히 MySQL에서 CPU·I/O 부하가 집중되는 병목이 관찰되었고,  
이를 계기로 검색 전용 엔진인 Elasticsearch를 도입하게 되었습니다.

---

### 2. 입찰 조회 API

입찰 조회 API는 경매 상세 화면에서 자주 호출되는 API로,  
여러 사용자가 동시에 입찰 내역을 확인하는 상황을 가정했습니다.

- 테스트 시나리오
  - 목표 TPS 160 달성 여부를 확인했습니다.
- 결과 요약
  - 평균 TPS: 180 TPS
  - 목표 TPS: 160 TPS

입찰 조회 API는 로컬 환경 기준으로 목표 TPS를 안정적으로 초과 달성했습니다.  
다만 일부 구간에서 응답 시간이 길어지는 모습이 관찰되어,  
쿼리 최적화와 캐싱 등을 통해 더 안정적인 응답 시간을 만들 수 있는 여지가 있다고 판단했습니다.

---

### 3. 입찰 API

입찰 API는 요청 빈도 자체는 상대적으로 낮지만,  
한 시점에 여러 사용자가 동시에 입찰하는 상황에서 안정성이 중요합니다.

- 테스트 시나리오
  - 분당 약 30회의 입찰 요청과 동시 사용자 30명을 가정했습니다.
  - 목표 TPS는 15로 설정했습니다.
- 결과 요약
  - 기본적인 목표 TPS는 달성 가능하다는 것을 확인했지만,
    입찰 검증 로직과 트랜잭션 처리 방식에 따라 응답 시간이 민감하게 변하는 모습을 확인했습니다.

이 결과를 바탕으로, 입찰 요청을 RabbitMQ 기반 비동기 처리 구조로 분리했고,  
입찰 검증 로직과 이벤트 처리 로직을 점진적으로 리팩토링할 계획입니다.

---

### 4. 정리 및 개선 방향

성능 테스트를 통해 다음과 같은 점을 확인했습니다.

- 검색 API는 RDB 기반 LIKE 검색 방식으로는 목표 TPS를 달성하기 어렵고,  
  Elasticsearch와 같은 검색 전용 엔진 도입이 필요했습니다.
- 입찰 조회 API는 목표 TPS를 초과 달성했지만,  
  일부 응답 지연 구간을 개선하면 더 안정적인 운영이 가능합니다.
- 입찰 API는 요청량 자체는 크지 않지만,  
  동시성, 검증 로직, 트랜잭션 처리 방식을 신경 써야 하는 구간임을 확인했습니다.
